# Emotion Labeling Task

A web interface for a **human labeling study** built for Human-AI Interaction assignment **A1-2**.
Each participant reads **5 randomly selected tweets** from the
[Emotion dataset](https://huggingface.co/datasets/dair-ai/emotion) and labels the emotion each one
expresses (anger, fear, joy, love, sadness, surprise, or "none of these / unsure"). The app records
**who labeled which tweet with which label**, and researchers can review and export the data from a
password-protected admin page.

- **Live demo** 
- **Stack:** Next.js 16 (App Router, TypeScript) as a single deployment for UI and API, Supabase Postgres in
  production, SQLite for local development.
- **Responsive:** mobile-first, and uses the whole screen on desktop; checked at 320, 375, 768, 1024 and 1440 px.
- **Themes:** Light, Dark or Auto (follows your device) from a switch in the header.

> The **bonus essay** on the ethics of AI emotion classification (based on Andalibi & Buss, 2020, and
> Stark & Hoey, 2021) is on the app's [Reflection page](content/reflection.md) at `/reflection`.

## 2. How it works (participant journey)

1. **Home (`/`)**: instructions, what is recorded, a content notice, the emotion guide, an optional
   nickname, and a **required consent checkbox**. "Start" stays disabled until consent is ticked.
2. **Task (`/task`)**: **one tweet per screen** with a progress bar ("Tweet 2 of 5"). For each tweet the
   participant picks one of 7 options (6 emotions + "None of these / Unsure"), rates confidence 1-5
   (required), and may add a short rationale. Each **Next** saves that answer to the server, so a refresh
   resumes exactly where they left off. **Back** lets them revise earlier answers until they submit.
3. **Debrief (`/done`)**: after **Submit**, they see their anonymous ID, their labels next to the
   dataset's labels (worded neutrally: "matches"/"differs"), and a note on why a single "ground truth"
   emotion label is questionable.
4. **Admin (`/admin`)**: password-protected table of every label, summary statistics, participant filter,
   and CSV download.

**One submission per browser:** a browser that has submitted sees "you have already taken part". A
"Start new participant (testing)" link clears the browser's session so graders/testers can run the task
again. It never deletes data already saved.

**Ground truth is hidden while labeling.** The dataset's label for a tweet is stored in the database but
is never included in any API response until the participant has submitted (verified by the e2e test).

## 3. Architecture

```
 Browser (React client components)                      Vercel (one Next.js deployment)
 ┌───────────────────────────────┐   fetch JSON   ┌────────────────────────────────────────┐
 │ /  /task  /done  /admin       │ ─────────────► │ app/api/**/route.ts   (thin handlers)  │
 │ components/*.tsx              │ ◄───────────── │   │ validate with zod (lib/validation)  │
 │ localStorage: participant ID  │                │   ▼                                     │
 └───────────────────────────────┘                │ lib/service.ts   (business rules)       │
                                                  │   │                                     │
                                                  │   ▼                                     │
                                                  │ lib/storage/index.ts  (picks back end)  │
                                                  │   ├─ supabase.ts ──► Supabase Postgres  │  production
                                                  │   └─ sqlite.ts   ──► .data/dev.sqlite   │  local dev / tests only
                                                  └────────────────────────────────────────┘
```

**Layering (why the code is split this way):**

- **Route handlers** (`app/api/**`) only parse/validate input and translate errors to HTTP responses.
- **Service** (`lib/service.ts`) holds *all* rules (random draw, "may only label your own tweets", "locked
  after submit", "needs all 5 labels", "results only after submit"). Written once, so it behaves the same
  on both databases and is unit-testable without HTTP.
- **Storage** (`lib/storage/*`) is a dumb persistence interface with two implementations.
- **Backend selection** (`lib/storage/index.ts`): Supabase if `SUPABASE_URL` and
  `SUPABASE_SERVICE_ROLE_KEY` are set; otherwise SQLite **only outside production**; in production without
  Supabase config it throws, so a deployment can never silently write to Vercel's ephemeral disk.

### Request flow for one tweet

`Next` click → `PUT /api/participants/:id/labels` → zod validates → `saveLabel` checks the participant exists,
is not submitted, and the tweet is one of *their* 5 → `storage.upsertLabel` → `{ ok: true }` → UI advances.
The PUT is idempotent, so retrying after a network error is safe.

## 4. Data model

Same logical schema in Postgres ([`supabase/schema.sql`](supabase/schema.sql)) and SQLite
([`lib/storage/sqlite.ts`](lib/storage/sqlite.ts)).

| Table | Purpose | Key columns |
|---|---|---|
| `tweets` | The pool of 60 tweets | `id`, `text`, `ground_truth` |
| `participants` | One row per participant | `id` (e.g. `P-7F3K9Q`), `nickname` (nullable), `consented_at`, `completed_at` |
| `assignments` | The 5 tweets drawn for each participant and their order | `participant_id`, `tweet_id`, `position` 1-5 |
| `labels` | **Who labeled which tweet with which label** | `participant_id`, `tweet_id`, `label`, `confidence` 1-5, `rationale`, `time_spent_ms`, `submitted_at` |

`label` is one of `anger, fear, joy, love, sadness, surprise, unsure` (enforced by a CHECK constraint).
`(participant_id, tweet_id)` is the primary key of `labels`, so a participant has at most one label per tweet.

## 5. API reference

All bodies are JSON. Errors look like `{ "error": { "code": "...", "message": "..." } }`.
Responses are sent with `Cache-Control: no-store`.

| Method & path | Body | Success | Errors |
|---|---|---|---|
| `POST /api/participants` | `{ nickname?, consent: true }` | `201 { participantId, tweets[5] }` (no ground truth) | 400, 503 (pool not seeded) |
| `GET /api/participants/:id` | | `200 { participantId, nickname, completed, tweets, labels }` | 404 |
| `PUT /api/participants/:id/labels` | `{ tweetId, label, confidence, rationale?, timeSpentMs }` | `200 { ok: true }` | 400, 403 (not your tweet), 404, 409 (already submitted) |
| `POST /api/participants/:id/complete` | | `200 { items[] }` **(first time ground truth is returned)** | 400 (unlabeled tweets), 404 |
| `GET /api/participants/:id/results` | | `200 { items[] }` | 403 (not submitted yet), 404 |
| `POST /api/admin/login` | `{ password }` | `200`, sets HttpOnly cookie | 401, 503 (admin not configured) |
| `POST /api/admin/logout` | | `200`, clears cookie | |
| `GET /api/admin/data` | | `200 { rows, stats }` | 401 |
| `GET /api/admin/data?format=csv` | | CSV download | 401 |

## 6. Run it locally

Requirements: **Node 22.13+** (developed on Node 24; uses the built-in `node:sqlite`).

```bash
npm install
cp .env.example .env.local        # leave the Supabase values blank locally
npm run dev                       # http://localhost:3000
```

With no Supabase variables set, the app uses a local SQLite file (`.data/dev.sqlite`) and seeds the tweet
pool automatically on first use. Open <http://localhost:3000>, complete the task, then open
<http://localhost:3000/admin> and log in with `ADMIN_PASSWORD` from `.env.local` (default in
`.env.example`: `change-me`).

| Script | What it does |
|---|---|
| `npm run dev` / `build` / `start` | Standard Next.js commands |
| `npm run seed` | Upserts `data/tweets.json` into the active database (Supabase if configured, else SQLite) |
| `npm run build-dataset` | Regenerates `data/tweets.json` from HuggingFace (deterministic) |
| `npm test` | Vitest unit tests |
| `npm run test:e2e` | Playwright end-to-end run, 22 tests (also regenerates the screenshots) |
| `npm run lint` | ESLint |

### Environment variables (`.env.example`)

| Variable | Required | Purpose |
|---|---|---|
| `SUPABASE_URL` | production | Supabase project URL |
| `SUPABASE_SERVICE_ROLE_KEY` | production | Server-side secret key. **Never** expose it to the browser or prefix it with `NEXT_PUBLIC_` |
| `ADMIN_PASSWORD` | for `/admin` | Shared password for the researcher page |
| `ADMIN_SESSION_SECRET` | production | Random string used to sign the admin cookie (`openssl rand -hex 32`) |

## 7. Deploy to Vercel + Supabase (single deployment)

SQLite files do **not** persist on Vercel (ephemeral filesystem), so production uses Supabase Postgres.

1. **Create a Supabase project** at <https://supabase.com> (free tier is fine).
2. **Create the tables:** Supabase dashboard → *SQL Editor* → *New query* → paste all of
   [`supabase/schema.sql`](supabase/schema.sql) → *Run*. (Row Level Security is enabled with no policies:
   only the server's service-role key can access the data.)
3. **Get the credentials:** *Project Settings → API* → copy the **Project URL** and the **`service_role`
   secret key**.
4. **Seed the tweet pool once** from your machine:
   ```bash
   SUPABASE_URL="https://xxxx.supabase.co" SUPABASE_SERVICE_ROLE_KEY="eyJ..." npm run seed
   ```
   Expect: `Seeded 60 tweets into Supabase; database now holds 60.`
5. **Push the project to GitHub**, then in <https://vercel.com> choose *Add New → Project* and import the
   repo (framework preset: Next.js, no build settings to change).
6. **Add environment variables** in *Project Settings → Environment Variables* (Production):
   `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`, `ADMIN_PASSWORD`, `ADMIN_SESSION_SECRET`.
7. **Deploy** (or *Redeploy* if you added the variables after the first build).
8. **Verify:** open the site, complete the task, then open `/admin`, log in, and confirm your labels
   appear. You can also see the rows in Supabase → *Table Editor → labels*.

**Render instead of Vercel:** create a *Web Service* from the repo with build command
`npm install && npm run build`, start command `npm start`, and the same four environment variables. Keep
using Supabase for the database. (SQLite on Render's free tier is also ephemeral.)

## 8. Testing

```bash
npm test            # 38 unit tests, ~0.2 s
npm run test:e2e    # 22 scripted browser tests, ~30 s (first time: npx playwright install chromium)
```

- **Unit tests** (`tests/`): random sampling (size, uniqueness, membership, rough uniformity), ID format,
  input validation, CSV escaping and formula-injection defence, admin token signing/expiry, and the whole
  service layer against an in-memory SQLite (dataset has ≥50 tweets over 6 emotions, 5 distinct tweets per
  participant, label upsert, ownership check, "need all 5 to submit", results hidden until submit, admin
  join).
- **End-to-end** (`e2e/flow.spec.ts`), on a fresh throwaway database:
  participant A completes the task on desktop (including keyboard shortcut, a mid-task page reload that must
  resume, and going Back to see a saved answer); asserts **no `groundTruth` in any pre-submission API
  response**; a completed browser cannot restart but can reset; participant B gets different tweets;
  participant C completes it on a 390 px phone with no horizontal overflow; the admin rejects anonymous and
  wrong-password access, sees all 15 rows with the right participant/label, filters, exports CSV, and signs
  out. It writes the screenshots to `docs/screenshots/`.
- **Responsive / dark mode** (`e2e/responsive.spec.ts`): at 320, 375, 768, 1024 and 1440 px, in light and dark
  colour schemes, a participant completes the task and every page (home, task, debrief, reflection, admin)
  is checked for horizontal page overflow.
- **Theme switch and wide layout** (`e2e/theme-layout.spec.ts`): Auto follows the device, Light/Dark override
  it and are remembered across reloads and pages, the switch fits a 320 px phone; on a 1470 px desktop the
  content area is wide, the start panel sits beside the instructions, and the tweet sits beside the answer
  controls.

**To produce your own "participant" screenshot by hand:** `npm run dev`, complete the task at
<http://localhost:3000>, then log in at `/admin` and screenshot the table.

The end-to-end tests start their own server on port 3100 with a throwaway SQLite database and their own
build folder (`.next-e2e`), so they never touch Supabase and can run while your own `npm run dev` is open.

## 9. UX / HCI design rationale

Mapped to Nielsen's usability heuristics and WCAG 2.2 basics:

| Principle | How the interface applies it |
|---|---|
| **Visibility of system status** | "Tweet 2 of 5" + progress bar; a live "Saving… / Saved" message; loading skeletons; clear thank-you state |
| **User control & freedom** | Back button; answers editable until submit; leave and resume later; "Start new participant" reset; consent is explicit and stopping is always possible |
| **Error prevention** | Consent gate before start; Next disabled until label + confidence are set, with the reason shown next to it; server validates everything; a submit-time warning that answers can't be changed |
| **Error recovery** | Failed saves show an inline message with **Try again**; the participant's input is kept; idempotent saves make retries safe |
| **Recognition rather than recall** | Emotion guide always one tap away; each option has an "i" with definition + example; keyboard shortcut hints on the cards |
| **Consistency & standards** | Fixed alphabetical option order (no emotion is visually favoured); native radio/checkbox/dialog semantics; one button style system |
| **Help & documentation** | Plain-language instructions, a "no right or wrong answers" statement, the emotion guide, content notice |
| **Aesthetic & minimalist design** | One tweet per screen, calm neutral palette, one accent colour; **no emoji or per-emotion colours** so nothing nudges participants toward a label |
| **Accessibility** | Semantic landmarks, one `h1` per page, labelled controls, skip link, visible focus rings, focus moved to the step heading on each step, `aria-live` status, selection shown by border + check + dot (not colour alone), ≥44 px tap targets, WCAG AA contrast, light/dark theme (device setting or the header switch), `prefers-reduced-motion` respected |
| **Responsive** | Mobile-first CSS that uses the full screen on desktop: content up to 1280 px wide, instructions beside the start panel on the home page, the tweet beside the answer controls while labeling, and tweet-by-tweet comparison beside the notes on the debrief. Option cards 1 / 2 / 3 columns by width; sticky Back/Next bar on phones with safe-area padding; admin table becomes labelled cards on phones; `100dvh`, `viewport-fit=cover` |
| **User preference (theme)** | A Light / Dark / Auto switch in the header. Auto (default) follows the device; a Light or Dark choice overrides it, is remembered in the browser and is applied before first paint, so there is no flash of the wrong theme. Icons only on phones, icons + text on wider screens |

**Human-AI-interaction choices in the study design:**

- An explicit **"None of these / Unsure"** option and a **confidence rating** avoid forcing a possibly wrong
  label and capture ambiguity, which is central to whether emotion can be "classified" at all.
- The dataset's "ground truth" is **hidden during labeling** to avoid anchoring, and revealed afterwards with
  neutral wording ("matches"/"differs", never "correct"/"wrong").
- The debrief explains that the dataset label is not an objective fact and links to the Reflection page.

## 10. Dataset provenance, ethics and privacy

- **Source:** `dair-ai/emotion`, `split` config, `train` split (16,000 tweets). Citation:
  Saravia, E., Liu, H.-C. T., Huang, Y.-H., Wu, J., & Chen, Y.-S. (2018). *CARER: Contextualized Affect
  Representations for Emotion Recognition.* EMNLP 2018. The dataset card lists the license as "other"
  and the annotations as "machine-generated"; check the card for terms of use before redistributing.
- **How the 60 tweets were chosen:** keep tweets of 8-40 words, drop duplicate texts, then pick **10 per
  emotion** with a seeded PRNG (mulberry32, seed 42). The script is deterministic: rerunning
  `npm run build-dataset` yields the same file. Text is shown **exactly as in the dataset** (lowercase, no
  punctuation, sometimes with artifacts such as "a href https www").
- **Label noise is real:** some dataset labels look questionable (for example a tweet about loving the feeling
  of running in the cold is labeled *anger*). That is expected and useful for discussing ambiguity.
- **Content notice:** tweets are unfiltered public text and may contain strong language or distressing
  feelings; the instructions say so and that participants can stop at any time.
- **Privacy:** the app stores an anonymous ID, an optional nickname, labels, confidence, optional rationale
  and per-tweet time. It does not ask for names, emails or accounts and sets no tracking cookies (only an
  HttpOnly admin cookie for researchers). Hosting providers may keep standard server logs.
- **Security:** service-role key only on the server; RLS enabled with no public policies; all input validated
  with zod; admin password compared in constant time; signed HttpOnly session cookie; CSV export defends
  against spreadsheet formula injection; rationale/nickname rendered through React (escaped).

## 13. Known limitations

- **No rate limiting** on the public API; fine for a class study, add e.g. Vercel's firewall or an
  upstash-style limiter for a larger deployment.
- **One submission per browser** is a soft limit (localStorage); clearing site data or another browser
  allows another participation (intended, so testers can retry).
- A participant ID acts as a bearer token for that participant's own session; it is unguessable
  (31^6 combinations) but not a full authentication system.
- The admin area uses one shared password, suitable for a course project, not for multiple researchers.
- Tweets are shown lowercase and unpunctuated exactly as in the dataset, which makes some hard to read; this
  was a deliberate faithfulness choice.
- Dev mode only: the app refuses SQLite in production by design.
